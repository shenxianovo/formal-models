# 软件工程的信息模型

> 表示、约束、选择与证据

## 1. 研究问题

构造和演化软件系统，需要不断回答问题：系统应该做什么、当前实现会做什么、线上发生了什么，以及为什么选择这种方案。代码、需求、接口定义、测试和日志，是回答这些问题的不同材料。

本模型研究：

**这些材料分别表达什么，哪些内容可以由已有材料确定，哪些需要补充选择或观测，以及怎样以可接受的成本维护这些关系。**

模型从“材料如何限制可能的答案”开始。规范、实现、运行状态、目标、证据，都在具体问题需要它们时进入模型。文件格式与工程分层不决定基本概念。

核心思路是：

> **内容用它排除和保留的可能情况刻画；推导用于得到已有内容保证的结论，决策用于选择尚未被确定的方案，观测用于取得关于实际情况的证据。工程上还要计入获取、理解、检查和维护这些信息的成本。**

## 2. 起点：表示、解释与可能情况

### 2.1 表示

**表示 A** 是承载信息的材料，可以是一句话、一段代码、一个配置项、一份接口定义、一条日志，也可以是这些材料的集合。

表示的形式与内容分别讨论。同一内容可以用自然语言、类型定义或逻辑公式表达；同一个文件可以同时包含需求、实现说明和设计理由。

对于一个批量处理接口，下面三个数值即使相同，也回答不同的问题：

- 契约规定的上限 r。
- 源码中的默认上限 c。
- 指定生产实例当前生效的上限 p。

r = 100、c = 100、p = 100 分别陈述三件事。判断重复之前，先确定陈述的对象与角色。

### 2.2 解释背景

**背景 K** 规定如何理解材料，包括讨论对象、版本、时间、单位、语言语义、系统边界，以及本次分析采用的假设。

例如“超时为 30”需要单位；“线上配置为 100”需要实例和时间；“接口必须接受 100 项”需要明确是在定义契约，还是报告实现行为。

K 中的假设需要能够被指认。正在检验的结论不能作为背景前提：检查实现是否满足契约时，不能预先假设实现已经满足契约。

### 2.3 可能情况与语义内容

固定 K 后，定义 **W_K** 为讨论范围内的候选情况集合。一个候选情况 w 可以给出相关变量、规范、实现、环境或历史的具体取值。只纳入当前问题需要的区分。

表示 A 的语义内容定义为：

\[
S_K(A)=\{w\in W_K\mid w\text{ 满足 A 所表达的声明}\}
\]

直观地说：**假定 A 的声明成立，还有哪些情况可能发生？**

例如，只研究一个正整数上限 x：

- “x 不超过 100”保留 x ∈ {1, …, 100}。
- “x 等于 80”只保留 x = 80。
- “x 为 80”和“x ≥ 80 且 x ≤ 80”保留同样的情况。

这是用满足关系刻画语义的做法。[1] 本模型将它用于比较软件材料中的声明。

**S_K(A) 刻画 A 说了什么。是否有理由相信 A，则由来源、观测和验证处理。** 一份错误文档仍然有可分析的内容。

自然语言存在多种解释时，先保留这些解释，或通过澄清选定其中一种。把“快一些”直接解释为“延迟小于 100 毫秒”，本身就是新增决定。

### 2.4 材料组合

用 Γ 表示本次分析共同采用的材料，其联合语义为：

\[
S_K(\Gamma)=\bigcap_{A\in\Gamma}S_K(A)
\]

交集表示“同时满足这些声明的情况”。它是**内容组合后的候选空间**，不是“重复信息的集合”。

当交集为空时，这组声明在 K 下无法同时成立。工程处理应定位冲突前提，修正内容或解释背景，再继续分析。

## 3. 从语义定义得到基本关系

以下关系都在同一背景 K 下比较。用于获取结论的前提集合应当可满足；空候选集表示冲突，不作为有效知识的起点。

| 关系 | 定义 | 回答的问题 |
| --- | --- | --- |
| 相容 | S_K(A) ∩ S_K(D) ≠ ∅ | 两份声明能否同时成立？ |
| 冲突 | S_K(A) ∩ S_K(D) = ∅ | 两份声明是否无法同时成立？ |
| 蕴含 | A ⊨_K D，当且仅当 S_K(A) ⊆ S_K(D) | A 成立是否保证 D 成立？ |
| 内容等价 | S_K(A) = S_K(D) | 两份声明是否作出了相同区分？ |

材料集合 Γ 对 D 的蕴含，同样写作 Γ ⊨_K D。

“x = 80”蕴含“x ≤ 100”，因为前者保留的每种情况都满足后者。逆向不成立：满足 x ≤ 100 的情况还包括 x = 60。

### 3.1 重复是相对于已有材料的关系

若 Γ ⊨_K D，则加入 D 不再缩小联合候选空间：

\[
S_K(\Gamma\cup\{D\})=S_K(\Gamma)
\]

此时称 **D 的声明内容相对于 Γ 冗余**。

这给出一个不依赖句子数量的重复判据。D 可能是一句概括，也可能是从多个文件经过复杂计算得到的长表格；只要它的声明已经被 Γ 保证，就不再增加这一语义范围内的限制。

反过来，若加入 D 后候选空间严格缩小且仍非空，D 提供了此前没有确定的内容。若变为空，则出现冲突。

局部重合可以通过共同蕴含的具体声明来展示。例如两份材料都蕴含“userId 是必填字段”，但其中一份还规定了错误码。全局重复率则需要另行约定问题范围、权重和度量方式。

### 3.2 更强的声明与更可信的声明

候选空间更小，表示声明更具体、约束更强。可信度回答声明与实际情况是否相符。

“生产上限一定是 80”比“生产上限在 1～100 之间”更具体；前一句是否正确，需要核实实际部署。内容强度与证据强度分别记录。

## 4. 以问题为单位比较信息

### 4.1 问题与可能答案

完整语义比较会涉及很多与当前任务无关的细节。因此引入 **问题 Q**：它从候选情况中取出我们关心的答案。

例如，Q(w) 可以是某个接口的参数类型、指定实例的上限，或“实现是否满足契约”的真假值。多个相关问题用联合答案表达，以保留答案之间的关系。

给定材料 Γ，可能答案集合为：

\[
\operatorname{Ans}_K(Q\mid\Gamma)
=\{Q(w)\mid w\in S_K(\Gamma)\}
\]

若这个集合只有一个元素，答案在当前材料与背景下已经被唯一确定。

若两组材料对 Q 给出相同的可能答案集合，称它们**对当前问题 Q 等价**。例如，源码与接口说明可能对“必填参数有哪些”给出相同答案，而源码还保留算法细节。

### 4.2 不能推出的直接判据

要判断一个答案是否被材料确定，可以寻找两个候选情况：它们都满足已有材料，但对 Q 给出不同答案。

只要存在这样的 w₁、w₂，就说明已有材料不足以唯一确定 Q。

例如，两段历史产生相同的限流代码：一段历史以控制成本为动机，另一段以保障公平为动机。源码无法区分这两段历史，因此不能据此确定原始动机。要恢复历史，需要加入决策记录、当事人陈述等来源。

从生成关系看也一样。若 A = f(H)，且 f(H₁) = f(H₂) 而 H₁ ≠ H₂，则 A 无法唯一反演 H。恢复实际的 H 需要能区分候选历史的额外信息。选择规则可以确定采用哪个候选，但不能单凭选择证明它就是真实历史。

### 4.3 关系本身也是内容

设 x、y 都只能取 0 或 1。材料 A 说 x = y，材料 B 对二者都不作限制。

单独询问 x，A 与 B 都给出 {0, 1}。加入材料 F：“y = 0”后：

\[
\operatorname{Ans}(x\mid A,F)=\{0\},\qquad
\operatorname{Ans}(x\mid B,F)=\{0,1\}
\]

A 保存的是变量之间的关系。它的价值在组合后显现。

因此，**当前问题等价只支持当前上下文中的替换判断；跨上下文复用需要保留相关的联合关系。** 完整内容等价则在加入相同额外声明后继续成立，因为相等集合与同一集合取交集仍然相等。

这也是代码与配置、规则与数据经常必须共同读取的原因：一份材料保存映射，另一份材料提供映射的输入。

## 5. 推导、生成、选择与观测

这些操作都可以产出新材料，但承担不同的信息工作。

### 5.1 推导：得到已有内容保证的结论

语义蕴含 Γ ⊨_K D 表达“所有满足前提的情况都满足结论”。

实际推导还需要推理方法。例如，指定证明系统 P 后，Γ ⊢_P D 表示存在该系统中的推导。证明系统相对于语义可靠时，推导得到的结论受到前提保证。[1]

工程上还要询问：当前工具是否能找到推导、是否能检查推导，以及需要多少时间和资源。

因此，将一个问题判为“输入不足”，需要不同答案的候选情况作为依据；工具超时或未找到证明，表示本次求解没有完成。

### 5.2 生成：执行一个产出材料的过程

设生成过程为：

\[
D=f(A_1,\ldots,A_n;\theta)
\]

θ 包含影响输出的工具版本、模板、模型、配置、默认策略与随机种子等。外部检索结果或运行观测也是输入，应当进入依赖记录。

固定完整输入和过程后，输出可以被确定。但“输出可重现”与“输出声明受到输入支持”分别验证。

一个始终输出“该接口保证幂等”的程序也是确定性的。它建立了生成关系，却没有因此建立源码与幂等声明之间的蕴含关系。

对描述性文档生成器，需要检查输出是否忠实表达输入。对编译器，需要检查生成程序与源程序的行为关系。CompCert 将这一要求写成独立的语义保持定理，而非用“成功生成代码”代替它。[6]

### 5.3 选择：确定一个尚未被约束唯一确定的方案

若已有要求允许多种实现，产出某个具体实现就包含选择。

“同一订单最多发放一次权益”可以由不同存储结构、事务方案和并发控制方式实现。选择数据库唯一约束，补充了原要求没有唯一规定的设计决定。

选择的依据可以来自成本、偏好、团队约定、模型中的默认策略或显式授权。固定生成器能够固定选择结果，但这些选择规则属于生成器及其输入，而非自动成为原始需求的内容。

**从需求构造实现，通常是推导、搜索与选择的组合。** 从实现提取说明，则通常是分析与投影。二者没有一般性的互逆关系。

### 5.4 观测：取得关于实际情况的记录

观测通过某个过程接触系统，产出日志、测量值、测试结果或部署回执。

一次测试定义说明“输入什么、预期什么、怎样比较”；一次测试结果记录“实际运行发生了什么”。测试定义与测试结果承担不同角色。

观测的新内容可能来自实际部署、输入、调度或故障条件。对于完全由已有材料和语义确定的结果，执行也可以主要承担计算工作，把难以直接读出的结论变成容易检查的记录。

## 6. 软件系统如何进入模型

### 6.1 先区分规范性内容与描述性内容

规范性内容规定允许什么、要求什么；描述性内容陈述实现和实际运行是什么样。

设契约要求批次校验对且仅对 1 ≤ n ≤ r 放行，某实现对且仅对 1 ≤ n ≤ p 放行。固定其他条件后，符合该契约的条件是 p = r。

“契约上限 r = 100”与“实现上限 p = 80”可以同时为真。二者描述了一个不符合契约的系统，而不是一组自相矛盾的陈述。

若两份描述分别声称同一实例、同一时刻 p = 80 与 p = 100，才是内容冲突。

因此应分别判断：

\[
\text{声明是否相容}\qquad\text{实现是否符合规范}
\]

前者是材料之间的逻辑关系，后者是材料所描述对象之间的要求关系。

### 6.2 行为符合关系

研究系统行为时，引入以下领域对象：

| 符号 | 含义 |
| --- | --- |
| M | 实现机制，包括本次系统边界内的代码、配置、数据与组件 |
| E | 考虑的输入、外部依赖和运行条件范围 |
| Beh(M, E) | 在该机制与环境范围下可能产生的行为 |
| R | 规格允许的行为集合 |
| π | 将实现行为映射到规格观察粒度的抽象方式 |

对逐条行为轨迹规定的要求，符合关系定义为：

\[
\boxed{\pi(\operatorname{Beh}(M,E))\subseteq R}
\]

π(B) 表示集合 B 中每条行为经过 π 映射后的结果。实现与规格已经使用同一观察粒度时，π 取恒等映射。

例如，实现中可能存在数据库访问、重试和队列消费等内部步骤；规格只关心订单是否成功、权益发放次数。π 负责说明如何比较这两种描述。

M 与 E 的边界按问题固定。把部署配置算作实现的一部分，或把它作为外部条件处理，都需要保持相同的解释。行为集合是由实现和环境定义的语义量；某份源码、一次执行记录只是关于它的材料。

对完成性要求，行为描述需包含持续运行、停滞或终止情形。“永远不发放权益”是一种需要检查的行为。规格同时表达“最多一次”与“满足前提时最终发放”，才能同时约束重复和遗漏。

性能概率目标可以作用于行为分布，跨运行的信息关系可以作用于行为集合。它们仍然是具体的符合性问题，由相应的问题 Q 与判定条件表达。

### 6.3 精化与形式化规格

**形式化规格**用具有明确语义的语言表达约束，使满足关系可以被精确讨论。

**精化**是在明确的抽象映射下，具体模型的行为受到抽象模型约束。用行为集合表达，就是具体行为经抽象后落入允许集合。Lamport 对状态式规格的精化讨论采用了这种通过行为与蕴含关系比较规格的思路。[5]

精化表达的是约束保持关系，不是文件的时间顺序。代码更长、设计更详细，也需要另外检查该关系是否成立。

### 6.4 目标与取舍

约束确定可接受的方案范围；目标和偏好用于比较范围内的选择，也用于决定采用哪些约束。

“系统稳定”转化成可用性、延迟和成本要求，需要作出阈值与取舍决定。满足同一要求的两个实现，也可以在维护成本和资源占用上不同。

目标、偏好和决策理由都可以作为材料进入同一信息模型，不需要固定成独立的文档层。一个方案符合已选规格，与这份规格是否服务于目标，是两个不同的问题。

## 7. 证据、来源与权威

### 7.1 区分声明内容与声明发生

“报告写着所有测试通过”与“被测系统满足要求”是不同声明。

要从前者得到后者，需要关于测试覆盖、预期来源、执行版本和检查机制的依据。来源信息记录材料如何产生，能够支持对质量和可信度的判断；W3C PROV 正是围绕实体、活动及其参与者表达这类来源关系。[7]

证据记录应能回答：检查的是哪个对象和版本，采用哪些输入与假设，执行了什么方法，得到什么结果，以及结果覆盖什么范围。

这些信息也是材料，使用相同的表示与依赖关系来分析。证据的作用取决于它支持哪个声明，以及支持所依赖的过程和前提。

### 7.2 观测的覆盖范围

假设在某版本上观察到若干执行通过检查，得到的是这些执行的记录。要把结论扩展到其他输入、并发交错或部署，需要覆盖性论证、统计假设或形式证明。

一个可重复的反例能够否定“所有相关执行都满足要求”。通过样例所支持的范围，则由样例选择与验证方法确定。

测试预期从契约获得，可以检查实现与契约之间的差异。预期直接复制实现输出，则主要检查输出稳定性或与既有快照的差异。两种检查应按其实际检验对象使用。

### 7.3 相同内容可以具有不同的证据结构

一份测试报告及其拷贝，与两个分别执行的检查，可能都写“通过”，但它们依赖的过程不同。

假设某类故障已经存在，每次检查漏报的概率为 p。复制一次检查的结果，两份报告共同漏报的概率仍是 p；两次检查在该故障条件下独立且漏报率相同，才得到 p²。检查数量本身不能决定这一概率。

工程上关心的是共同失效来源，例如共享同一错误预期、同一遗漏路径或同一错误配置。不同工具或不同作者，并不自动消除共同失效来源。

另一方面，证明证书可以完全由已有定义推导而来，却把“寻找证明”变成“检查证明”。它的价值可以来自较低的检查成本和明确的可信基础，而不需要新增独立事实。

### 7.4 权威是采纳规则

对一项规范或设计决定，权威来源规定“采用哪个定义，以及谁可以改变它”。对事实判断，来源则需要通过证据评价。

例如，契约文件可以定义允许的批次大小；生产配置报告描述已部署值。修改生产配置不会自动改写契约，修改契约也不会自动证明部署已完成。

对于同一项需要主动维护的决定，指定明确的规范表达位置，可以减少重复决策。其他表达可以派生，验证材料则保留各自的检查作用。

**定义的权威、声明的真实性、检查的覆盖范围，是三个分别回答的问题。**

## 8. 信息量与获取成本

### 8.1 先有问题，再定义概率模型

语义集合回答哪些答案仍可能成立。需要衡量不确定性的多少时，再为候选情况或材料生成过程指定概率分布。

固定背景 K，令 X 是问题 Q 的答案这一随机变量，A、D 是可能取得的材料。以下采用离散变量，并在熵差公式中要求相关熵有限。定义：

\[
H(X)=-\sum_x P(x)\log_2P(x)
\]

H(X) 衡量平均不确定性，单位为 bit。[2]

分布可以来自明确的抽样过程，也可以是分析时声明的假设。同一个固定文件的字数、字节数与 H(X) 是不同的量。

### 8.2 增量信息

给定材料 A，材料 D 对 X 的平均增量定义为条件互信息：

\[
I(X;D\mid A,K)
=H(X\mid A,K)-H(X\mid A,D,K)
\]

它比较取得 D 前后的平均条件熵。[2][3] 因此需要给出问题、材料变量和联合分布。

这里的“减少”是对观测结果取平均。某一次具体观察可能让原本看起来很确定的问题变得更不确定，例如暴露出先前忽略的分支。[3]

统计上的零增量与逻辑上的可推导性分别判断：概率为零的候选情况仍可能在逻辑模型中存在，换一个分布也可能改变信息量。

### 8.3 确定性视图

若 D = f(A; θ)，且完整 A、过程 θ 和背景 K 都已给定，则在该随机变量模型中：

\[
H(D\mid A,\theta,K)=0
\]

\[
I(X;D\mid A,\theta,K)=0
\]

给定这些条件，D 的输出没有剩余不确定性。这一结论既适用于正确的生成器，也适用于错误的生成器；内容正确性由语义关系检验。

代码生成的接口文档、查询索引和计算结果，可以在这一意义上不增加信息，同时显著改变使用者获得答案所需的工作。

### 8.4 组合信息与协同

设 A、D 是独立且等概率的二进制变量，目标 X = A ⊕ D。则：

\[
I(X;A)=I(X;D)=0,\qquad I(X;A,D)=1\text{ bit}
\]

单独知道任何一个输入，都无法确定 X；知道两者即可确定。这样的组合效应是协同信息的典型例子。冗余、独有贡献和协同贡献的区分，是多变量信息分解研究所处理的问题。[4]

该例还给出：

\[
I(X;D\mid A)=1\text{ bit}
\]

因此，条件互信息表示给定 A 后的增量，其中可以包含组合效应；不能直接将它命名为“D 自己独有的信息”。

软件中的对应结构是：配置规则与配置值、迁移脚本与迁移前状态、协议规则与消息序列。重要内容可能位于关系之中。

### 8.5 获取成本

信息已被语义确定，还需要使用者找到、读懂、计算并检查答案。为此，对明确的使用者 U、工具 T、任务 Q 与质量标准，评价获取答案的成本：

\[
\operatorname{Cost}_{U,T}(Q\mid\Gamma)
\]

成本可以分别记录时间、计算资源、人工投入和检查工作。相同内容的两种表示可以有不同成本。

由此区分三个工程问题：

| 问题 | 典型证据 | 对应动作 |
| --- | --- | --- |
| 材料不足以确定答案 | 存在满足相同前提但答案不同的候选情况 | 补充观测、决策或来源 |
| 答案已受前提约束，但获取昂贵 | 复杂推导、大量检索、求解超出预算 | 改进表示、索引、计算与检查方法 |
| 材料给出答案，但缺少可信依据 | 来源不明、版本不符、覆盖不明 | 核实来源、补充验证 |

文档和工具的价值可以来自降低后两种成本，而不是增加新的业务事实。

### 8.6 衡量一组材料

评估时明确问题范围、已知材料、语义背景、使用者、工具和质量标准。

内容分析可以报告具体的蕴含、冲突、未确定项与组合依赖。概率分析可以在给定分布下报告熵和增量。工程评估则测量获取与维护成本、错误发现能力和残余风险。

“多少内容可删”还取决于未来任务、来源留存、恢复成本和验证用途。针对一个问题的信息等价，不直接构成整个工程系统中的删除授权。

## 9. 组织信息：权威定义、派生视图与检查关系

### 9.1 三种处理依据

面对一项材料内容，先确定它的作用：

**需要选择的定义。** 记录采用了什么、适用范围是什么、谁有权改变。规格阈值、架构方案和兼容性策略属于此类。

**可以从完整输入得到的视图。** 记录输入、过程、版本以及所保证的语义范围。根据更新成本决定随用随算还是保留生成物。

**用于检验声明的材料。** 记录检查对象、预期来源、执行条件和覆盖范围。根据错误模式评价它的作用。

这三种作用可以出现在同一文件中。组织原则作用于内容与关系，而非文件扩展名。

### 9.2 依赖包含联合前提

一个结论可能需要多个输入共同成立：

\[
\{A_1,A_2,\ldots,A_n;K\}\longrightarrow D
\]

例如，只有源码、实际生效配置和部署版本共同确定，才能给出指定实例的行为结论。

因此，依赖记录需要表达“这组输入共同支持这个结论”，以及关系属于生成、逻辑推导、设计选择还是经验检查。一个简单的“相关文件”链接不足以表达这些差别。

### 9.3 变更处理

变更首先区分两种情况：获得了同一对象的新信息，还是改变了对象、规范或环境。

新信息可以与现有材料组合。新的规范版本或部署版本则改变了讨论对象，应替换当前适用的前提，并重新评价依赖它的结论。

例如，昨天的部署上限为 80、今天为 100，是两个带时间的事实；把时间省略，才会制造表面的冲突。

对一处变更，沿其实际依赖关系分别执行：重新生成视图、重算结论、复查原有证据、检验仍生效的约束，或重新作出选择。

**修复描述，改变实现，修改要求，是三种不同的变更。** 当实现违反要求时，更新实现说明只能让描述更准确；恢复符合性需要改变实现或经过授权重新选择要求。

### 9.4 工程优化目标

维护材料的目标是：在既定业务目标和可靠性要求下，降低决策、获取、构造、验证和演化的总成本。

为此，减少不必要的独立维护，保留能降低读取成本的视图，并保留能够发现重要错误的检查与证据。

最少文件、最少字数和最低内容冗余，都只是可能影响成本的因素。需要优化的是整个任务与演化过程，而非某个单独计数。

## 10. 完整实例：一个批量处理接口

### 10.1 固定讨论范围

讨论接口版本 v 的批次大小校验。请求均已通过鉴权，内容合法，其他检查通过；批次大小 n 是正整数。契约和实现都使用整数阈值规则：不超过阈值则放行，超过则拒绝。

讨论时刻为 t，生产实例为 u。

### 10.2 材料

**契约 N**：版本 v 的最大批次为 100。因此，关于这项校验，应对且仅对 1 ≤ n ≤ 100 放行。

**源码 C**：

```text
limit = 已设置且合法的 MAX_BATCH，否则取 80
允许请求，当且仅当 1 <= n <= limit
```

**部署材料 F**：已核验实例 u 在 t 时刻运行版本 v，进程实际生效的 MAX_BATCH 为 60。

**实现说明 D**：根据 C 生成，说明默认阈值为 80，设置 MAX_BATCH 时采用配置值。

**运行记录 O**：在 u、t 上，n = 90 的请求因批次大小校验被拒绝。

**契约测试 T**：根据 N 定义，n = 100 应放行，n = 101 应拒绝。运行环境明确绑定到被测配置。

### 10.3 分别能知道什么

| 问题 | 所需材料 | 结论 |
| --- | --- | --- |
| 契约规定多少？ | N | 100 |
| 源码默认多少？ | C 或 D | 80 |
| 指定实例生效多少？ | C 与 F | 60 |
| n = 90 那次发生了什么？ | O | 因批次大小校验被拒绝 |
| 仅凭 O 能否确定阈值为 60？ | O | 只能由阈值规则得到 p < 90，无法唯一得到 60 |
| 指定实例是否符合该契约？ | N、C、F | 不符合，61～100 项会被实现拒绝 |
| 是否已观察到违约执行？ | N 与 O | 是，n = 90 按契约应放行，却因这项校验被拒绝 |
| 为什么最初选择默认 80？ | N、C、D、F、O | 这些声明没有区分不同的历史理由，需要决策来源 |

C 与 D 在默认值和覆盖规则上有重复内容。N 与 C 表达不同角色的信息，数值不同本身不是逻辑冲突。C 与 F 组合得到有效阈值，体现联合依赖。

O 与 C、F 的推导结果相容，并提供这次执行的记录。结合 N，O 已经构成一个违约反例；定位到精确阈值 60，则需要 C、F 提供的额外信息。观测能够否定普遍符合性，而无需枚举全部执行。

### 10.4 如何修复

若保留 N，实例 u 的生效阈值需要改为 100，并验证变更实际生效。默认值是否同步改为 100，取决于契约是否也覆盖未设置 MAX_BATCH 的部署；覆盖时就需要修正该路径。

实现说明 D 继续忠实描述 C。契约测试 T 的预期仍来自 N，用于发现实现与要求之间的差异。

若业务决定将契约改为 60，则这是一次规范变更，需要处理对应客户端与兼容性要求。更新接口文档本身不能代替这次决定。

### 10.5 新增需求如何传播

现在把某个新契约版本的上限定义为 120。首先改变的是规范选择，而不是自动得到了新的实现。

随后确定适用范围与兼容性，更新相关实现和配置，重新生成契约视图及实现视图，并运行对应边界检查。最终通过部署和运行材料确认实际采用的版本与参数。

旧执行记录仍描述旧对象。关于新版本的符合性，需要与新前提相匹配的证据。

## 11. Agent 在模型中的位置

Agent 是执行推导、生成、选择、观测编排与检查的机制。模型本身按操作与关系分类，因此这些工作既可以由人承担，也可以由编译器、生成器、验证器或 Agent 承担。

一项 Agent 任务应说明：给定哪些材料和背景，要回答什么问题或作出什么选择，允许修改哪些定义，以及什么证据足以接受结果。

当任务是提取视图时，检查提取内容与输入之间的关系；当任务是实现需求时，检查候选方案满足的约束，并记录新增决定；当任务是解释故障时，区分候选解释与实际证据；当任务是传播变更时，按依赖种类处理相关结论。

评估 Agent 的作用，可以比较相同任务和质量标准下的总成本、错误类型及检查成本。生成速度只占其中一部分。

由此，AI 辅助开发可以被组织为：

**明确问题与约束 → 补充必要决定或观测 → 构造与派生 → 检查关系 → 根据证据继续调整。**

这是一组可重复组合的操作，不要求每个项目采用同样的文件层次或固定流程。

---

## 12. 模型的整体含义

代码、文档、测试和日志不是四个天然独立的信息源，也不是可以相互替换的四种文字格式。它们是带有不同语义、来源和使用成本的表示。

其中有些内容已经由其他材料保证，适合成为派生视图；有些内容规定新的选择，需要明确维护；有些内容记录观测或检查，用于评价关于系统的声明。

软件开发因此包含三类持续发生的工作：**决定与构造，表达与派生，检验与修正。** 三者通过明确的前提、要求和依赖相连。

本模型的工程原则是：

> **对需要选择的内容明确其定义与权限；对可以派生的内容明确其输入和过程；对需要相信的声明明确其证据；对持续变化的系统维护这些关系的适用范围。**

## 附录 A：最小检验集

这些小例子用于检验模型中的定义和推论。

| 检验 | 输入 | 应得结果 |
| --- | --- | --- |
| 表达不同，内容相同 | 同一对象 30 秒与 30000 毫秒 | 在单位换算背景下等价 |
| 数值相同，角色不同 | 契约 100 与默认配置 100 | 两项不同声明，需另外检查符合性 |
| 相容但不合规 | 契约精确阈值 100，实际阈值 80 | 声明相容，实现不符合契约 |
| 同一对象的内容冲突 | 同一实例同一时刻阈值既为 80 又为 100 | 候选集合为空 |
| 生成不保证内容 | 任意源码都生成“保证幂等” | 存在生成关系，缺少一般性的语义保证 |
| 多对一丢失信息 | 两段动机历史产生同一代码 | 代码不足以唯一恢复动机 |
| 组合得到答案 | x = y 与 y = 0 | 联合确定 x = 0 |
| 当前问题等价不可任意替换 | x = y 与无约束，随后加入 y = 0 | 替换前后对 x 的答案不同 |
| 完整内容等价可组合 | S(A) = S(D)，加入相同 F | S(A ∧ F) = S(D ∧ F) |
| 零信息增量仍有用 | 完整输入与固定过程生成查询视图 | 输出已被确定，读取成本可降低 |
| 内容相同，证据过程不同 | 报告拷贝与分别执行的检查 | 根据来源和共同失效模式评价 |
| 未要求的行为不自动成为要求 | 只要求最多发放一次 | 未表达必须最终发放 |
